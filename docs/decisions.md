# 决策记录

> 格式：`日期 · 决策 · 理由`。只记「为什么不那样做」，不重复文档里已经写清楚的实现细节。

---

## 2026-10-31 · 技术栈对齐 Mile Terminal

采用 Electron 43.4.0 + electron-vite 5 + React 19 + TypeScript 5.9 + Tailwind 4 + zustand 5 + node-pty 1.1 + xterm 6，版本逐项抄 `mile-terminal-management@2.3.0`。

理由：那套组合在本机已经过 54 个真实进程 harness 验证，`node-pty` 的原生模块与 Electron ABI 匹配、`preload` 沙箱配置、NSIS 打包链路都跑通过。新项目换版本只会重新踩一遍原生模块与沙箱的坑。

## 2026-10-31 · 终端内嵌，不用外部 Windows Terminal

用 node-pty（ConPTY）+ xterm.js 内嵌渲染，而不是 `wt.exe` 起外部窗口。

理由：外部窗口里看不到内容，无法左右分屏、无法在侧栏显示运行状态、也无法记录退出码。外部 Windows Terminal 保留为右键菜单里的一个便利入口（`shell:openExternalTerminal`），不是主路径。

## 2026-10-31 · 侧栏结构：分组 > 工作区

不做「分组 > 项目 > 多个 agent」三层。

理由：用户的真实诉求是「同一个目录可能用不同 agent 各开一次」，那本质是多个工作区指向同一目录，不需要中间层。三层结构会让侧栏在 20 个工作区时过深。

## 2026-10-31 · 浅深双主题，默认跟随系统

两套令牌都要做，不做只做浅色。

理由：终端类应用夜间使用比例高；而参考项目的深色令牌已经成型，直接沿用成本低。默认跟随系统，用户可手动锁定。

## 2026-10-31 · 宫格布局：1 / 2 / 4 三种固定布局（初稿为「最多左右两屏」，用户答复后修正）

会话数量不设 UI 上限（软上限 12 个进程），可见的格只有 1 / 2 / 4 三种。格与会话的对应关系可拖拽交换，布局持久化。

理由：用户明确要「四宫格、左右两个或者单个」并自行调整会话位置。只提供三种固定布局而不做自由拖拽缩放，是因为自由宫格在 1024 宽的窗口里最小格会低于 360px，agent 的 TUI 会挤到不可用；固定布局能保证每格最小尺寸。不做标签页——会话通过侧栏树和格来承载，比标签页更能看清「哪个会话在哪个格」。

## 2026-10-31 · 关闭窗口提供「最小化到托盘」与「全部结束并退出」

默认不直接退出；两种方式都写会话快照。

理由：agent 任务动辄跑十几分钟，误关窗口的代价高。托盘常驻让用户在关闭窗口后仍能收到 agent 的输出。同时保留「全部结束并退出」，避免托盘模式下用户找不到彻底退出的入口。

## 2026-10-31 · 会话快照 + 一键恢复，而不是自动恢复

启动后在空态卡片里让用户点一次；设置项可改为自动恢复。

理由：用户原话是「下次打开仅需点一键启动」。自动恢复会在用户只想看一眼配置时凭空拉起几个 agent 进程、消耗 token，默认必须显式确认。恢复是「重新启动进程并续接上次对话」，应用自己不重放历史输出。续接方式见下一条。

## 2026-10-31 · 目录栏是只读目录树（独立一列）

不做新建、重命名、删除，不做双击打开文件。

理由：agent 自己就在改这些文件，应用再提供写入口会出现两边同时改的冲突；而且应用没有编辑器和撤销能力，误删无法恢复。只读目录树解决的是「看清 agent 改了哪些文件」，不是「当文件管理器用」。

## 2026-10-31 · 目录栏不做自动轮询

首版只提供手动刷新；「有更新」提示列为可选。

理由：目录树对大项目（`node_modules`）轮询会持续占用磁盘 IO，而 agent 写文件的频率并不高，用户点一下刷新足够。真要自动化，走 `fs.watch` 的递归监听在 Windows 上也有句柄与性能问题，留到有明确需求再做。

## 2026-10-31 · agent 直接作为 PTY 进程启动

不先开 PowerShell 再在里面敲 agent 命令。

理由：直接启动才能拿到准确的退出码（PRD T-15 依赖它），也避免参数经 shell 二次解析。代价是退出后没有 shell，用「在此目录打开 Shell」按钮补偿；`keepShellOnAgentExit` 作为可选开关保留。

## 2026-10-31 · 绕过 npm 生成的 `.cmd` 批处理壳

解析 shim 后直接启动 `node.exe` + js，或直接启动 shim 指向的 exe；只有解析不出目标时才退回 `cmd /d /s /c`。

理由：批处理壳在 Ctrl+C 时会弹 `Terminate batch job (Y/N)?`，cmd 还会二次解释 `& | %` 等字符。`codex` 在本机只有 `codex.cmd`，这条路必须走通。

## 2026-10-31 · 不设 `FORCE_COLOR`

与 Mile Terminal 的做法相反。

理由：部分 agent 检测到 `FORCE_COLOR` 会改变配色或跳过 TTY 判断，而本项目本来就跑在真 PTY 里。颜色交给 agent 自己判断更安全。M0 实测后如果发现某些 agent 在 ConPTY 下不出色，再按需补上并记录原因。

## 2026-10-31 · 会话输出在渲染层保活，不在主进程重放

屏幕切换时把 xterm 容器挪进隐藏池，而不是销毁后回放原始字节流。

理由：全屏 TUI（alternate screen、绝对光标定位）回放原始字节流很难保证画面一致；保活实例最稳。代价是内存（每个会话一个 xterm，上限 12 个会话、5000 行回滚）。主进程仍保留 400k 字符环形缓冲，只用于渲染层重载后的兜底回放。

## 2026-10-31 · WebGL 只给可见屏

`WebglAddon` 只挂在当前可见的格上（最多 4 个），隐藏时 dispose，显示时重载；加载失败回落 DOM 渲染器。

理由：Chromium 单页 WebGL 上下文数量有上限（约 16 个），12 个会话各挂一个会互相挤掉。可见屏只有 2 个，够用。

## 2026-10-31 · `Ctrl+C` 有选区时先复制

照 Windows Terminal 的行为，不照 PRD 初稿「一律交给 agent」。

理由：终端用户对 `Ctrl+C` 复制已有肌肉记忆；有选区时发送中断还会让 agent 误以为用户要取消。无选区时仍照常发送中断。已同步修改 PRD T-07。

## 2026-10-31 · 外链放开到任意 http/https

Mile Terminal 只放行 localhost，本项目放宽。

理由：Claude Code、Codex 的登录授权流程会在终端里打印任意 https 授权链接（T-13），只放行 localhost 会让登录走不通。风险由「必须由终端内点击触发 + 仅 http/https」两条限制兜住，记入技术设计 §7。

## 2026-10-31 · 环境变量的值加密落盘

用 Electron `safeStorage`（Windows 下是 DPAPI）加密，且不下发渲染层。

理由：工作区环境变量里大概率会出现 `ANTHROPIC_API_KEY`、`OPENAI_API_KEY` 这类值。明文 JSON 落在 `%APPDATA%` 下不合适，发给渲染层更没必要。

## 2026-10-31 · 不引入单元测试框架

沿用 Mile Terminal 的 `scripts/verify-*.cjs` 真实进程 harness。

理由：本项目的风险集中在「PTY 行为、进程清理、IPC 边界、UI 实际渲染值」，这些都不是单元测试能覆盖的。真实 Electron 进程里 `executeJavaScript` 驱动的断言才是有效证据。

## 2026-10-31 · 三栏布局（会话栏 + 目录栏 + 宫格），取消底部状态栏

初稿是「侧栏上下分块 + 底部状态栏」，用户给出参考图后改为：最左会话栏、第二列目录栏、右侧宫格控制台。

理由：参考图把目录树放成独立一列，可以单独显隐，窄窗口下先收目录栏就能保住四宫格每格 360px 的下限；上下分块的侧栏在 260px 宽里两棵树都挤。状态栏在参考图里没有，四宫格又吃纵向空间，会话数和 agent 版本改放托盘提示与设置页。配色、字体、圆角仍用本项目令牌，不照搬参考图的灰色。Claude 徽章底色同时从 `#d97757` 改为 `#b8461f`，白字对比度由 3.12:1 提到 5.34:1。

## 2026-10-31 · 一键恢复续接上次对话，ID 获取按 agent 区分

Claude 由应用生成 UUID 并用 `--session-id` 指定；Codex、Kimi 没有指定 ID 的参数，启动后从各自的会话目录里发现。

不选「只用 `--continue` / `--last`」的理由：它只续接该目录下**最近一个**对话，同一目录开两个会话时两个会串到同一段对话上。所以快照里存每个会话各自的 `resumeId`；拿不到 ID 且同目录有多个会话时，宁可新开并在恢复卡片上标明，也不静默串对话。同一 `(agent, 目录)` 的会话恢复时逐个启动，避免「启动之后新增」的匹配有歧义。

不选「只重新启动」的理由：用户要的是重启电脑后点一下就接着干活，新开一个空对话等于没恢复。

## 2026-11-01 · 单击工作区卡片定位已有会话，不再开一个

PRD 4.2 第 4 步写「再次单击同一工作区可再开一个会话」，UI 文档 §4.1 写「点击卡片直接定位到该会话」，两处冲突，按 UI 文档做：有会话就切过去（优先运行中的），没有才启动；再开一个走右键「新建会话」。

理由：单击会拉起 agent 进程、消耗 token。连点两下就多出一个 agent 的代价太高，而「切回正在跑的会话」是更高频的动作。

## 2026-11-01 · 工作区卡片不做双击改名

PRD 4.4 写「双击工作区名称修改显示名称」。分组标签和会话子行支持双击 / F2 行内改名，工作区卡片不支持，改名走右键「编辑工作区」。

理由：双击的第一下就是单击，会先启动 agent。分组标签单击只是折叠，会话子行单击只是切换，都没有副作用，所以这两处保留双击改名。

## 2026-11-01 · 应用内确认框替代 window.confirm / alert

照 Mile Terminal 的 `Confirm.tsx` 做 `confirm()` / `notifyError()`，默认焦点在「取消」。

理由：原生对话框阻塞渲染线程，harness 的 `executeJavaScript` 会一起卡住，删除分组、删除运行中工作区这些确认路径就测不到；原生框的样式也不跟主题走。

## 2026-11-01 · 工作区卡片上不放「⋯」按钮

UI 文档只给分组标签行设计了悬停「⋯」，卡片的菜单走右键与键盘（菜单键 / `Shift+F10`）。

理由：200px 宽的卡片已经放了徽章、名称、格号小标和会话数胶囊，再加一个 28px 按钮，名称只剩约 60px。

## 2026-11-01 · 宫格相关菜单项随 M3 一起加

PRD W-11 列的「在第 1–4 格打开」「移到第 N 格」在 M2 不出现，也不画禁用占位。

理由：M2 只有一格，这些项点了没有意义；UI 文档 §4.1.1 对未做的页签也是同样处理（不画禁用占位）。

## 2026-11-01 · 实底按钮的文字改用 `--text-inverse`

主按钮、危险按钮、标题栏 logo 原来是固定白字。

理由：深色主题下 accent `#7aa7ff`、fault `#f87171` 都偏亮，白字对比度只有 2.5–2.8:1，不到 4.5:1。`--text-inverse` 浅色是白、深色是 `#0f1219`，两套主题都达标。Claude / Kimi 徽章底色两套主题相同且偏深，仍用白字。

## 2026-11-01 · 「在第 N 格打开」与拖卡片到格：先接回后台会话，没有才新开

PRD T-03 写「右键或拖拽：指定目标格启动」。实现为：该工作区有不在任何格里的运行中会话，就把它放进目标格；没有才在目标格新开。明确要新开一个走「新建会话」。

理由：与单击卡片的规则（decisions 2026-11-01 第一条）一致，避免拖一下就多起一个 agent。单击与指定格的区别只在目标格：单击用聚焦格，且该工作区已有会话显示在某格时只聚焦那格。

## 2026-11-01 · 自动收栏只在 2 格 / 4 格时生效

UI 文档 §3 的「控制台不足 744px 先收目录栏」按两列格子推算（2 × 360 + 8 + 16）。单格只需要一列，1024 宽两栏全开时控制台 584px 已经够一格 360，所以单格不自动收。

## 2026-11-01 · 窗口变窄时比例按尺寸夹取，存下的比例不改

分隔比例存的是用户拖出来的值；渲染时按当前容器尺寸夹到「两侧都 ≥ 360×240」的范围。窗口变宽后自动回到用户的比例。

理由：如果把夹取后的值写回存储，用户临时缩一下窗口，原来的比例就丢了。

## 2026-11-01 · 格间分隔条命中区 8px，等于格间距

UI 文档写「视觉 2px，命中区 6px」。格间距本来就是 8px，分隔条直接占满这 8px，中间画 2px 线。栏位边缘的拖拽条也是 8px，压在边框上。

理由：命中区做成 6px 要额外的负边距或绝对定位，换来的 2px 差别用户感觉不到。

## 2026-11-01 · 窗口状态多存一个 `maximized`

技术设计 §4 的 `LayoutState` 没有这个字段。最大化时只记标志，不覆盖还原尺寸；下次启动先按还原尺寸建窗，再最大化。上次的位置不在任何屏幕上（拔了副屏）时不用这个位置。

## 2026-11-01 · 恢复候选 = 上次运行时没被手动关闭的会话，记录随生命周期即时写盘

`SessionRecord` 加 `open`（用户没手动关闭）与 `kind`（agent / shell）。启动、拿到续接 ID、改名、退出、关闭时立刻写盘；应用退出期间（`shutdown`）被我们结束的进程不写退出码。下次启动时 `open = true` 的记录就是候选，本次运行新开的会话不进卡片。

不选「只在退出时写一次快照」的理由：技术设计 §5.8 规则 1 要求 ID 一拿到就落盘，应用崩溃、被强杀时也能恢复。不选「退出码照写」的理由：自动恢复（S-08）靠 `lastExitCode === null` 认出「上次还在跑」，退出时被结束的进程如果写了 1，就全被当成正常结束了。

`CONFIG_VERSION` 不升：两个新字段读盘时按缺省补齐（`open = false`、`kind = 'agent'`），旧记录不会被误当成候选。

## 2026-11-01 · 同目录多个 Codex 会话：有歧义就不写 ID

技术设计 §5.8 的调整写的是「按会话启动先后匹配新 rollout」。实现改为：新 rollout 出现时，同目录只有一个待认领的 Codex 会话才认领；有多个就把这个文件标为已看过，谁都不给。恢复时这几条按规则 3 标「新开」。

理由：首条消息先发的不一定是先启动的那个会话，按启动顺序匹配会把对话串错，而串错比新开的代价大。

## 2026-11-01 · 关闭确认框默认不记住，勾选「下次不再询问」才写 closeAction

PRD S-05 写「记住上次选择」。如果每次都自动记住，确认框只会出现一次，而改回「每次询问」要等 M5 的设置页。所以做成复选框，默认不勾。

## 2026-11-01 · 托盘图标由程序绘制

技术设计 §5.7 规划的是 `resources/tray.ico` 与 `tray-active.ico` 两个文件。M4 先用 `nativeImage.createFromBitmap` 画：品牌蓝圆角方块加白色「>_」，运行中在右下角加绿点。正式图标资源随 M5 的 NSIS 打包一起做。

理由：现在仓库里没有任何图标资源。程序绘制不依赖打包路径（`asar` 里的资源路径在开发和打包两种形态下不同），M4 能直接验证托盘行为。

（已被替换：后来改用设计稿生成的图标，见下文「应用图标用设计稿，统一由脚本生成」。）

## 2026-11-01 · 格子占满时，恢复卡片收进标题栏入口

UI 文档只规定了恢复卡片放在空格里。harness 发现：恢复出的会话填满所有格后，取消勾选的候选就没有地方显示了。现在的规则是：有空格时卡片放在第一个空格里；没有空格时，标题栏中间出现「恢复上次的 N 个会话」入口，点开以对话框显示同一张卡片。

## 2026-11-01 · 开发期允许用 MILE_WARP_AGENT_HOME 改 agent 会话目录

`ResumeDiscovery` 默认读真实主目录下的 `~/.codex/sessions` 与 `~/.kimi-code/session_index.jsonl`。只在 `!app.isPackaged` 时认这个环境变量，供 `verify-m4-restore.cjs` 把这两个目录指到沙箱。

理由：验证 Codex / Kimi 的 ID 认领，需要假 agent 往这两个目录写文件，不能写进用户真实的会话目录。打包后不认这个变量，没有额外的攻击面。

## 2026-11-01 · 去掉 Electron 默认应用菜单

`Menu.setApplicationMenu(null)`；开发期用 `before-input-event` 保留 F12 开发者工具。

理由：默认菜单的加速键会在按键到达终端之前被处理：`Ctrl+R` 重载页面、`Ctrl+W` 关窗口、`Ctrl+=` / `Ctrl+-` / `Ctrl+0` 缩放整页。这违反 PRD T-18「焦点在终端时，除 Ctrl+Shift 组合与字号快捷键外全部交给 agent」。而 `Ctrl+R` 在 PowerShell 和 bash 里是反向搜索历史，`Ctrl+W` 是删前一个词，都是高频键。`verify-m5-settings.cjs` 第 1 步用 stdin 探针确认这两个键原样进了 PTY。

## 2026-11-01 · 默认 Shell 只能从本机探测到的几项里选

`agent:shells` 返回本机实际存在的 PowerShell 7 / Windows PowerShell 5.1 / cmd；`settings:update` 的 `shellPath` 不在这个列表里就拒绝。

理由：`shellPath` 会被主进程直接 `spawn`。如果接受渲染层给的任意路径，就违反技术设计 §8 第 1 条「可执行文件不可由渲染层指定」。读盘时仍接受配置文件里手写的路径（用户自己编辑文件，不经过渲染层）。

## 2026-11-01 · 字号快捷键写进设置

`Ctrl+=` / `Ctrl+-` / `Ctrl+0` 改的是 `settings.fontSize`，所有终端同步，重启后保持。

理由：设置页里本来就有字号这一项，快捷键只是它的快捷入口。如果只改当前终端、不落盘，同一个窗口里各格字号会不一致，而且设置页显示的值和实际字号对不上。

## 2026-11-01 · 不做 keepShellOnAgentExit

`Settings` 里保留这个字段（兼容旧配置），设置页不显示，启动逻辑也不读它。

## 2026-11-01 · cmd-wrap 自己拼命令行，不交给 node-pty 转义

`.cmd` / `.bat` 还原不了 npm shim 时经 `cmd.exe /d /s /c` 启动。原来把参数数组交给 node-pty，它只在参数含空格时加引号，不转义 `& | % ^ < >`，工作区参数 `a&b` 会被 cmd 拆成两条命令。现在由 `commandResolver.spawnArgs()` 拼整条命令行：每个参数先按 CommandLineToArgvW 规则加引号，再给 cmd 元字符加 `^`，参数转两遍（cmd 解析一次，批处理里的 `%*` 展开后再解析一次），壳路径转一遍。node-pty 收到字符串时原样使用；`execFile` 版本探测配 `windowsVerbatimArguments`。`LaunchSpec.args` 仍保存原始数组，便于诊断。

否决的方案：遇到元字符直接拒绝启动（参数里的 `%`、`&` 在 URL、正则里很常见，拒绝太粗）；引入 cross-spawn（违反「不引入新依赖」，而且它是 child_process 封装，不覆盖 node-pty）。由 `scripts/verify-cmd-wrap.cjs` 把关，node-pty 与 execFile 两条路径各跑一遍。

## 2026-11-01 · 启动参数开头的命令名自动去掉；退出时归档旧批次的恢复候选

两个问题叠在一起，表现为「恢复后每个会话都冒出一条 claude 消息，而且一次恢复很多个」：

1. 工作区参数写成了 `claude --permission-mode bypassPermissions`。命令由应用按 agent 解析，参数里再带一个 `claude`，Claude Code 会把它当成第一条用户消息。`lib/launchArgs.stripLeadingCommand` 在启动时去掉最前面与 agent id / 命令名相同的词（忽略大小写和 `.exe/.cmd` 后缀，只去一个）；工作区保存时也去掉。
2. 恢复候选只增不减：每次退出，没手动关的会话都保持 `open=true`，下次启动没恢复也没忽略的又留着，一键恢复就把所有批次一起拉起。`SessionRecords.archiveStale` 在退出时调用：本次运行开过会话，就把启动时已有的可见候选归档（`open=false`）；本次什么都没开就退出，旧候选原样保留。目录缺失、工作区已删的记录不是可见候选，不动。

否决的方案：启动时就归档（用户还没来得及看恢复卡片，旧会话就丢了）；只保留最近 N 条（N 没有依据，且仍会混批次）。

理由：marked（52KB）已独立成 MarkdownView chunk 不进首屏；Phosphor 新 icon 改成 `components/previewIcons.tsx` 只取 regular path（每个 ~0.4KB，省 ~16KB 全套 defs）。剩下的 ~14KB 是预览栏本体（rail 组件 + zustand + 布局字段）确实该占的位置 —— 它是常驻 UI 不是弹窗，不能 lazy。再往下压只能拆通用 helper 或换 icon 库，收益小、复杂度高，不值。

2026-11-05 · 对抗审查补的三处：codeload 覆盖仅开发期、条目名逐段校验、tar 预检按名单比对 | `MILE_WARP_CODELOAD_OVERRIDE` 原来打包后也认，能把 GitHub 安装悄悄改到任意 http 源，现在与其它 MILE_WARP_TEST_* 一样 `!app.isPackaged` 才认；zip / tar 条目名含 `:`（NTFS 备用数据流，readdir/lstat 看不见、cpSync 会带进目标）、Windows 保留设备名、以点或空格结尾的段一律拒绝；tar 预检原来按行内是否含 " -> " 判断链接，文件名本身带箭头会误拒，改为对照 `tar -tzf` 名单看行尾是不是条目名本身。

2026-11-05 · 放宽「不执行 git」：只在设置「启用 Git 管理」打开后执行，默认关（Git管理-PRD §6.1） | 原决策是为了不碰用户仓库配置和 hooks；但 agent 改完文件后要切工具看 diff、提交，是最高频的出窗口动作。改成显式总开关：关着时应用零 git 进程，行为与之前一致，`GitInfoService` 读 `.git/HEAD` 不变；打开后由主进程按 workspaceId 取目录执行，参数数组 + 环境清洗 + 超时。界面放右栏页签（与预览共用槽位）+ 工作台弹窗，不做格内面板（要把 `cells` 改成联合类型，牵动宫格、恢复、托盘全链路）。主进程用 simple-git（源项目同款，纯 JS、不进渲染包），不引入 better-sqlite3（工作区本身就是仓库登记，省掉原生模块重编）。提交照常跑仓库 hooks，等同用户在命令行提交。升级建议 §3.8 的目录栏改动标记并入（G-18），复用同一次 `git status`。

2026-11-05 · GitService 的 git 子进程固定加 `-c core.fsmonitor=false -c core.quotepath=false` 与 `GIT_OPTIONAL_LOCKS=0` | 仓库配置里的 `core.fsmonitor` 是任意命令，`git status` 会执行它，打开一个不受信任的仓库就等于运行它的代码，所以每条命令都在命令行上把它关掉（命令行 `-c` 优先于仓库配置，verify-git 用恶意配置实测）；quotepath 关掉免得中文路径被转义成八进制；agent 可能同时在同一仓库跑 git，status 不抢 `index.lock`。只认 PATH 里的 `git.exe`，不走 `git.cmd`（要经 cmd.exe）。simple-git 的 `allowUnsafeCustomBinary` / `allowUnsafeFsMonitor` 两个放行是因为：前者的字符校验拒绝 `C:/Program Files/...` 里的空格，路径来自主进程 PATH 查找、不来自渲染层；后者拦的正是我们用来关 fsmonitor 的 `-c core.fsmonitor=false`。
