# 踩坑记录

## 2026-11-01 · M0 PTY 探针

### node-pty：进程已退出后再 `kill()` 会打印 `AttachConsole failed`

- 现象：`taskkill /T /F` 结束进程树之后再调 `pty.kill()`，控制台冒出 `conpty_console_list_agent.js ... Error: AttachConsole failed`。
- 原因：`kill()` 会 fork 一个辅助进程去 attach 目标控制台列出子进程，目标已经不在了，attach 失败。报错发生在辅助子进程里，不影响主进程。
- 对策：先 `taskkill`，等 `onExit`；只有进程仍未退出时才 `pty.kill()`。SessionService 照此实现。

### ConPTY 下 Node 子进程的 `resize` 事件不可靠

- 现象：`pty.resize(90, 20)` 后，子进程 `process.stdout.on('resize')` 没触发，但 `process.stdout.columns` 已经是 90。
- 对策：验证尺寸时轮询 `columns/rows`，不依赖事件。真实 agent（TUI 框架）自己会处理，不影响产品。

### 脚本里写入原始控制字符导致 Edit 匹配失败

- 现象：用 Python/sed 往探针脚本里插 `'\x1b'` 时，替换串被解释成真的 ESC 字节写进了源码，之后 Edit 工具按文本匹配一直失败。
- 对策：往源码里写转义序列时用独立脚本读写文件（`String.raw` 或 `'\\x1b'`），写完用 `od -c` 检查控制字节数为 0。

### Codex 在新目录首次启动会弹 hooks 信任框

- 现象：探针在临时目录启动 `codex`，停在「Hooks need review」选择框，后续界面不出现。
- 影响：自动化探针无法在不代答的前提下进入主界面；产品里由用户自己在终端里选择，Mile Warp 不代答。

## 2026-11-01 · M1 单格终端

### zustand 选择器里写 `?? []` 导致 React #185（无限重渲染）

- 现象：渲染层报 `Minified React error #185`，空态卡片渲染不出来，harness 找不到工作区卡片。
- 原因：`useConfig((s) => s.config?.workspaces ?? [])` 在 config 为 null 时每次返回新数组，zustand 判定状态变化，触发重渲染，循环。
- 对策：选择器只返回 store 里的原引用（`s.config?.workspaces`），兜底空数组放到组件里，或用模块级常量 `EMPTY`。

### harness 用 `| tail` 时卡住看不到进度

- 现象：验证脚本卡在某一步，`tail` 要等进程结束才输出，5 分钟什么都看不到，还留下 10 个 electron 进程。
- 对策：输出直接重定向到文件；脚本自带总超时（`setTimeout(...).unref()` 后 `app.exit`）；收尾用 `Get-CimInstance Win32_Process` 按命令行确认是本项目的进程再 `taskkill`。

### 往源码里插字符串时换行被写成真换行

- 现象：用内联 node 脚本给 harness 打补丁，`'\n'` 被 shell 与 JS 两层解释，源码里出现跨行字符串，`node --check` 报 `Invalid or unexpected token`。
- 对策：与 M0 的控制字符问题同一类，补丁逻辑写成独立脚本文件；改完跑 `node --check`。

## 2026-11-01 · M2 会话栏与目录栏

### harness 输出在 Windows PowerShell 5.1 下中文乱码

- 现象：`npx electron scripts/verify-fs-guard.cjs > log` 后读日志，中文全是「鍚堟硶璺緞」这类乱码，只能靠 PASS / FAIL 判断结果。
- 原因：PowerShell 5.1 按控制台代码页（GBK）解码子进程的 UTF-8 输出，`>` 又按 UTF-16 写文件。
- 对策：先设 `[Console]::OutputEncoding = [System.Text.UTF8Encoding]::new($false)`，再 `2>&1 | Out-File <log> -Encoding utf8`。已写进 CLAUDE.md。

### 合成 DragEvent：dragover 和 drop 连发时 drop 读到旧状态

- 现象：harness 在同一个 `executeJavaScript` 里依次派发 dragstart / dragover / drop，卡片的插入位置没生效。
- 原因：卡片在 dragover 里 `setDropAt('before')`，drop 处理函数读的是闭包里的 `dropAt`。同一个任务里连发事件，React 还没重渲染，drop 拿到的仍是 `null`。真实拖拽会有很多次 dragover，不会遇到。
- 对策：harness 把 dragstart、dragover、drop 分成三次 `executeJavaScript`，中间各等 50–100ms。

### 「快捷键没漏进终端」不能靠比对终端文本

- 现象：按 `Ctrl+Shift+B` 前后比对 xterm 缓冲区文本，结果总是不同。
- 原因：折叠会话栏让终端变宽，xterm 重排、PowerShell 跟着重绘提示符，文本本来就会变。
- 对策：在终端里跑一个 raw 模式回显 stdin 的 node 进程，按完快捷键断言没有 `GOT"..."` 输出；再发一个普通字符，断言能收到 `GOT"x"`，证明探针本身有效。

### nvm 切到 Node 22 后 codex 不在 PATH

- 现象：`verify-m1-session.cjs` 的「codex 可用」失败，`where.exe codex` 找不到。
- 原因：`C:\nvm4w\nodejs` 指向当前 nvm 版本，codex 只装在 v20.19 的全局包里，当前切在 v22.23。不是代码回归。
- 对策：跑 harness 前在当前会话前置 `C:\Users\LHmile\AppData\Local\nvm\v20.19.0` 到 PATH，或 `nvm use 20.19.0`。前置后 M1 27/27 通过。

## 2026-11-01 · M3 宫格

### sendInputEvent 拖动时 mouseMove 要带 `leftButtonDown`

- 现象：harness 用 `webContents.sendInputEvent` 模拟拖分隔条，6 次 mouseMove 只生效了第 1 次（拖 300px 只动了 50px，拖栏宽 60px 只动了 10px）。
- 原因：mouseMove 没带按键状态，Chromium 当作按键已松开，pointer capture 随即释放，后续移动不再发给分隔条。
- 对策：mouseMove 加 `modifiers: ['leftButtonDown']`。合成 `PointerEvent` 不行，`setPointerCapture` 对不存在的活动指针会抛 `NotFoundError`，必须走 sendInputEvent。

### 窗口缩窄后格子低于 360px

- 现象：四宫格拖出 0.63 的左右比例，再把窗口缩到 1024 宽，右列只剩 294px。
- 原因：比例只在拖动时按容器尺寸夹取，窗口尺寸变化后没有重新夹。
- 对策：`Grid` 用 ResizeObserver 跟踪容器尺寸，渲染时按尺寸夹取比例（`fitRatio`），存储的比例不改。`verify-m3-grid.cjs` 第 8 步覆盖。

### 渲染层重载时格位可能被误清

- 现象（设计时发现，未实际触发）：布局先读回、会话列表还没读回时，用空列表去 `prune` 会把所有格位清空，而这些会话其实还在主进程里运行。
- 对策：`sessions` store 加 `ready`，`prune` 只在会话列表和布局都读回之后执行。`verify-m3-grid.cjs` 第 10 步覆盖重载场景。

## 2026-11-01 · M4 关闭、托盘与恢复

### 改完主进程忘了重新 build，harness 跑的是旧产物

- 现象：`verify-m4-restore.cjs` 里 Kimi、Codex 的 ID 全是 null，而假 agent 确实往沙箱写了 session_index 和 rollout。
- 原因：`MILE_WARP_AGENT_HOME` 的支持是在 `npm run build` 之后才加进 `index.ts` 的；harness 加载的是 `out/`，发现服务还在读真实主目录。
- 对策：改完源码先 build，再跑 harness。CLAUDE.md 常用命令里已写明 harness 跑的是 `out/` 产物。

### 一个进程里没法「重启应用」

- 现象：验证一键恢复需要「退出 → 再启动」，但 Electron 主进程退出后 harness 也跟着结束了。
- 对策：`verify-m4-restore.cjs` 分成编排进程和阶段进程。编排进程不开窗口，用 `spawn(process.execPath, [脚本, --phase=N, --sandbox=…])` 依次起 3 次真实应用。阶段进程把 PASS / FAIL 逐行打印出来，由编排进程汇总；阶段进程由应用自己退出（测的就是退出流程）。

### 假 agent 的参数不要从终端输出里读

- 现象（设计时规避）：长参数在窄格子里会折行，ConPTY 还可能在折行处插入光标序列，从终端缓冲里用正则匹配不可靠。
- 对策：假 agent 把 `process.argv` 写到 `argv/<pid>.json`。走 npm shim 时会话的 `pid` 就是 node 进程本身，harness 按 pid 读文件。

### 恢复出的会话占满格子后，剩下的候选无处显示

- 现象：取消勾选一条、恢复其余 6 条后四格全满，恢复卡片（只放在空格里）消失，「忽略」按钮点不到。
- 对策：没有空格时，标题栏出入口，点开以对话框显示同一张卡片。见 decisions 2026-11-01。

## 2026-11-01 · M5 设置、快捷键与打包

### 默认应用菜单抢走 Ctrl+R / Ctrl+W

- 现象（设计时发现）：Electron 默认带一个应用菜单。`titleBarStyle: 'hidden'` 只是看不见它，加速键照样生效：在终端里按 `Ctrl+R` 会重载整个页面，按 `Ctrl+W` 会关窗口。
- 对策：`Menu.setApplicationMenu(null)`，开发者工具改成开发期的 F12。`verify-m5-settings.cjs` 用 stdin 探针确认 `\x12`、`\x17` 原样进了 PTY，页面没有重载。

### 改 APPDATA 环境变量挡不住打包后的应用写真实目录

- 现象：安装包冒烟脚本给打包后的 exe 设了 `APPDATA=<临时目录>`，结果应用读的仍是真实的 `%APPDATA%\mile-warp`，还在那里建了 Chromium 缓存和 `window-state.json`。
- 原因：Windows 上 Electron 的 `appData` 来自 `SHGetKnownFolderPath(FOLDERID_RoamingAppData)`，不读环境变量。
- 处理：那个目录是这次测试刚建的，里面没有 `config.json`，已按创建时间确认后删除。新增 `MILE_WARP_DATA_DIR`（见 decisions），冒烟脚本改用它，并在结束时断言真实目录没有被创建。
- 顺带发现：`userData` 与配置目录是同一个目录（包名就是 `mile-warp`），Chromium 缓存和 `config.json` 放在一起。这不影响使用，记下来备查。

### CDP 的 Runtime.evaluate：Promise 被拒时 result 里仍有对象

- 现象：冒烟脚本里 `session.start` 失败了，下一项「收到 Shell 输出」却报 PASS。
- 原因：`awaitPromise` 的表达式被拒时，返回里同时有 `exceptionDetails` 和 `result`，只看 `result.value` 会误判。
- 对策：`exceptionDetails` 有值就按 `undefined` 处理。

### verify 里 `[role="tab"]` 撞到目录栏的「文件」页签

- 现象：断言设置页有五个页签，实际选到了六个，第一个是目录栏的「文件」。
- 对策：选择器限定在 `[data-testid="settings-dialog"]` 里。全局 role 选择器在 harness 里都要加容器前缀。

### 设计稿的「透明背景」是画进像素里的棋盘格

- 现象：`docs/玻璃质感AI智能体控制面板.png` 看上去是透明底，读出来所有像素 alpha 都是 255，灰白棋盘格就是像素本身。
- 对策：`make-icon.cjs` 从四条边泛洪填充，只走「近乎中性灰、且不太暗」的像素（r/g/b 最大差 ≤ 22，最小分量 ≥ 90），得到背景遮罩。图形外沿是饱和的蓝色描边与光晕，泛洪越不过去；齿轮、机器人这些白色部分被蓝色包住，所以不会被误删。之后丢掉小于 2000 像素的前景碎块，再用 3×3 平均把边缘做软。

### nativeImage 的位图是预乘 alpha

- 现象：抠图后的位图交给 `nativeImage.createFromBitmap(...).resize()`，缩小后棋盘格又出现在图形周围。
- 原因：Skia 位图是预乘 alpha 的 BGRA。透明像素的 RGB 仍保留着原来的灰色，属于非法的预乘数据，缩放插值时就把颜色带了回来。
- 对策：写位图前把 RGB 乘上 alpha；`toBitmap()` 读回来的也是预乘值，叠到黑底上时直接用，不要再乘一次 alpha。

### 未解决：退出时偶发崩溃 / 偶发残留一个 agent 进程

- 现象：换图标后连续跑 8 次 `verify-m4-restore.cjs`，6 次全过，2 次各有一项失败：
  - 一次第 2 次启动在「全部结束并退出」后以 `0xC0000005`（3221225477，访问冲突）退出。快照与进程清理都已完成，崩溃发生在最后退出那一步。
  - 一次第 3 次启动退出后，有 1 个假 agent 进程 500ms 后仍在（编排脚本收尾时已清掉）。
- 已知：换图标之前跑过 4 次，都通过。这次退出路径上的改动只有托盘图标的来源（从 PNG 缩出两张，代替程序绘制）。现有数据不足以判定是图标改动引起的，还是 node-pty / ConPTY 在进程退出时的既有竞态。
- 待办：退出流程里加日志，记下每个 `killEntry` 的耗时、超时次数和 `tray.destroy` 的时序；反复跑这个脚本，确认崩溃点。在那之前，`quitAll` 后可能有个别 agent 进程残留，手动结束即可。

## 2026-11-01 · 布局修复、工作区图标、性能

### 不分层的元素样式会压过 Tailwind 工具类

- 现象：删除环境变量的按钮写了 `text-fault`，显示出来却是普通文字色。
- 原因：`tokens.css` 里的 `button { color: inherit }` 没有放进 `@layer`。Tailwind v4 的工具类都在 `@layer utilities` 里，而不分层的规则优先级高于所有分层规则，跟选择器权重无关。
- 对策：元素级默认样式（`button`、`*:focus-visible`、全局 `nowrap`）一律放进 `@layer base`。`verify-layout.cjs` 会检查危险按钮的计算颜色是否等于 `text-fault`。

### 文字被挤成两行：基线扫描的发现

- 1024 宽四宫格里，「重新检测」「选择」这类短按钮被 flex 压缩到折行，设置行的说明文字被挤到不足 100px 宽。
- 判定折行时要看单个文本节点有几个不同的行盒 top，不能拿整个元素的高度判断，否则图标和文字的垂直错位会被误判成折行。

### 验证脚本直接调 IPC，渲染层 store 不会跟着变

- 现象：脚本里 `window.warp.workspace.edit(...)` 换图标后，会话栏一直不显示新图标。
- 原因：主进程只在调用方的返回值里给新配置，没有广播；只有经 `useConfig` 的动作调用时，store 才会替换配置。
- 对策：要验证界面变化，就走界面（弹窗保存）；直接调 IPC 只用来验证主进程行为和落盘结果。

### 目录栏大目录慢在主进程，不全在渲染层

- 2000 个文件的目录，改动前展开要 655ms。拆开测量后，一部分是渲染 2002 个节点，另一部分是主进程逐个 `await lstat` + `stat`，一共 4000 次串行调用。
- 对策：渲染层分批渲染（每批 300 项），主进程改成并发 16 个（libuv 线程池默认只有 4 个线程，并发再高也没有用）。

## 2026-11-01 · 按《升级建议》升级

### 改了设置页签数，M5 的后续断言连锁失败

- 现象：`verify-m5-settings.cjs` 一次报 9 项失败，看上去字号、字体、命令面板都坏了。
- 原因：「五个页签」写死了页签列表；新加「通知」页签后它失败，之后设置页里的输入框选择器跟着落空，字号、字体、滚动行数几项全挂，命令面板两项是设置页没正常关闭带出来的。把页签断言改成六个后，49/49 通过。
- 另外：「Ctrl+W 送进 PTY」只在 `verify:all` 里排在其他脚本后面跑时失败（连续 3 次），单独跑 `npx electron scripts/verify-m5-settings.cjs` 连续 3 次都通过；渲染层没有任何代码处理 `KeyW`。推测是前面脚本留下的窗口焦点或系统按键状态影响了 `sendInputEvent`，不是应用代码的问题，原因未查明。`verify-m4-restore.cjs` 偶发的「退出后残留 1 个 agent 进程」也照旧出现过一次，重跑通过；新增的退出日志（`shutdown.begin` / `session.disposeAll.stuck` / `shutdown.killed`）可以用来追这个问题。
- 对策：断言失败要先看是哪一项最早失败，后面的失败多半是它带出来的，别逐条去修代码。

### 对比度用例选错了颜色

- 现象：「对比度不够的颜色被拒」没有被拒。
- 原因：`#888888` 配黑字约 5.3:1，本来就合格；黑白二选一时，中灰其实很难两边都不到 4.5。换成 `#777777`（黑字 4.2、白字 4.48）后才是真正不合格的例子。
- 对策：写颜色边界用例时先算一遍两种前景的对比度。

### 直接调 IPC 改分组颜色，界面不会变

- 与「验证脚本直接调 IPC，渲染层 store 不会跟着变」是同一个坑：`group:setColor` 返回新配置，但只有经 `useConfig` 的动作才替换 store。验证色带要走分组菜单。

### 单击卡片总在聚焦格打开

- 现象：harness 想把两个工作区分别放进第 1、2 格，结果第二个顶掉了第一个。
- 原因：单击工作区卡片在聚焦格打开；切到两格后聚焦格还是第 1 格。
- 对策：先在第 2 格上触发 mousedown 让它成为聚焦格，再点卡片。

### heredoc 里的反斜杠和引号

- bash heredoc 写 Python 补丁脚本时，`'\'` 这类字面量会被吃掉，脚本直接语法错误。按 CLAUDE.md 的规则，改源码的脚本一律先写成独立文件再运行。

### node-pty 的参数数组不防 cmd 二次解释

- 现象：工作区参数里有 `a&b`、`%PATH%`、`p|q` 时，走 cmd-wrap 的 agent 收到的参数被拆开或展开。
- 原因：node-pty 的 `argsToCommandLine` 只在参数含空格 / Tab 时加引号、转义引号前的反斜杠，不处理 cmd 元字符；`cmd /s /c` 会再解释一遍，`.cmd` 里的 `%*` 展开后又解释一遍。只转一遍时 `a"&"b`、`p|q`、`<>`、空参数、结尾反斜杠都会出错（实测）。
- 对策：`commandResolver.spawnArgs()` 自己拼整条命令行，参数转两遍、壳路径转一遍，以字符串交给 node-pty；`execFile` 要配 `windowsVerbatimArguments: true`，否则 Node 会再加一层引号。壳路径含空格、`&`、括号也已实测通过。

### 恢复后每个会话都多出一条「claude」消息

- 现象：恢复出多个 Claude 会话，每个对话的第一条用户消息都是 `claude`，Claude 回「你只发了个 claude」。
- 原因：工作区启动参数写成了 `claude --permission-mode ...`，第一个词被当成提示词。另外退出时没处理的恢复候选每次都留着，一键恢复会把多个批次一起拉起。
- 对策：启动时 `stripLeadingCommand` 去掉开头的命令名；退出时 `archiveStale` 归档旧批次候选。见 decisions 同日条目。

### harness 里 codex 找不到

- 现象：`verify-icons` 最后一项「格头显示工作区图片」失败，日志是 `找不到 codex 的可执行文件`。
- 原因：当前 shell 在 Node 22，codex 只装在 nvm 的 v20.19 下（CLAUDE.md 已记）。

## 2026-11-01 · 会话历史与全量回归

### 「窗口没关」不能用 `isVisible()` 断言

- 现象：`verify-m5` 的「Ctrl+W 送进 PTY，窗口没关」连续失败，但探针里 `\x17` 明明到了 PTY。
- 原因：`BrowserWindow.isVisible()` 在窗口被最小化时也是 false。运行环境把窗口最小化后（有人在用这台机器、或多个 harness 窗口抢焦点），断言误报；`\x17` 不受影响照常送达。
- 对策：断言语义改成 `!win.isDestroyed()`；按键前 `if (win.isMinimized() || !win.isVisible()) { win.restore(); win.show() }`。

### 高负载下 resize → 自动收栏超过 waitFor 窗口

- 现象：`verify-m3` 「1024 宽下目录栏临时收起」连续两轮失败，目录栏就是不收；单独重跑又全过。
- 原因：逻辑本身没问题（独立探针缩到 1023 即收起）。连续跑 15 个 harness 时渲染进程被拖慢，`win.setSize` 后的 resize → 重排超过 3 秒的 waitFor 窗口。
- 对策：排查时给 `__warpDebug` 加了 `layout()`（暴露 viewport / 栏位偏好 / override / railsOf 结果），harness 断言失败时把快照打进日志，下次再抖能直接看到是不是状态问题。

### 首屏 JS 预算卡线：小图标别内联

- 现象：`verify-perf` 首屏 JS 911KB > 900KB 预算。大头不是新代码：四个 agent 图标和 pi.png 共约 8KB，被 Vite 默认的 4KB 内联阈值转成 base64 进了主包（≈10.6KB JS）。
- 对策：渲染层 `assetsInlineLimit: 0`，图标落成文件由 `<img>` 异步取；新增纯图标按钮优先复用主包里已有的图标模块，不再为单个图标引入新模块。

### 断言终端文字要小心折行

- 现象：`verify-upgrade` 广播输入「另一格也收到」连续失败，hook / 格位 / 会话状态全部正确，手动 `session.write` 也能回显。
- 原因：功能本身没问题。窄格（~62 列）里 PowerShell 的提示符把行占满，'Q' 回显在末列、'Z' 折到下一行；`text()` 按 `\n` 拼行，`includes('QZ')` 天然失败。沙箱临时路径长度随机，正好卡在边界 → 表现为时好时坏。
- 对策：断言多字符输入时先 `text.replace(/\r?\n/g, '')` 再比较；排查手段：`__warpDebug.hookStats()`（onData 计数 / hook 拦截数 / apply 丢弃切片记录）+ `window.warp.session.buffer()`（主进程侧缓冲，区分 PTY 没回显与渲染层丢数据）。

### harness 环境残留 `ELECTRON_RUN_AS_NODE`

- 现象：验证脚本在 Electron 下启动却报 `app.setPath` is undefined，栈里有 `node:electron/js2c/node_init`。
- 原因：shell 会话里残留的 `ELECTRON_RUN_AS_NODE=1` 被子进程继承，Electron 以纯 Node 模式跑，`require('electron')` 不返回 API。
- 对策：跑 harness 前 `unset ELECTRON_RUN_AS_NODE`（或在新会话跑）。

### 空闲 TUI 的「重绘噪声」把会话顶成「对话中」

- 现象：Claude 会话明明空闲，格头与卡片却一直显示「对话中」。
- 原因：node-pty 实测（60 秒空闲 2 个 chunk）确认 TUI 会周期性重绘状态栏，内容是纯光标定位 / 擦除序列（如 `\x1b[9;39H\x1b[K\x1b[62C`），没有任何可见文字；但 `lastOutputAt` 被任何输出刷新，active 状态反复续命，永远落不回 quiet。
- 对策：`flush()` 里先剥 ANSI 转义与控制字符，还剩非空白字符才更新 `lastOutputAt`（`ANSI_STRIP_RE` / `hasVisibleOutput`）；verify-upgrade 加了「纯转义噪声不算 active」回归断言。注意 OSC 序列可能是 BEL 或 ST 结尾。
### RailResizer 贴错边：右边栏的分隔条飘出屏幕

- 现象：预览栏（最右）加了 `RailResizer` 后用户拖不到分隔条，预览栏宽度改不了。
- 原因：`RailResizer` 硬编码 `-right-1`（贴栏右边缘），是给左边栏（会话栏 / 目录栏）设计的——分隔条探出去压到中间区域才有命中区。预览栏在最右侧，`-right-1` 把分隔条画到了窗口右缘外的 8px，鼠标根本碰不到。
- 对策：加 `side?: 'left' | 'right'` 参数；`side='right'`（默认）换算 `clientX - rail.left`，`side='left'` 换算 `rail.right - clientX`（栏越窄越拖左）。预览栏传 `side="left"`，分隔条挂在 `-left-1` 压到预览栏和目录栏交界处。verify-preview 加了「分隔条在预览栏左边缘 8px 内」断言。

## 2026-11-05 · Git 管理 G0

### simple-git 拒绝带空格的 git.exe 路径

- 现象：`binary: 'C:\\Program Files\\Git\\cmd\\git.exe'` 直接抛 `Invalid value supplied for custom binary`。
- 原因：simple-git 3.36 对 `binary` 做字符白名单 `^([a-z]:)?([a-z0-9/.\\_~-]+)$`，空格不在内。放行 `allowUnsafeCustomBinary` 后又报 `spawn C:Program FilesGitcmdgit.exe ENOENT`，反斜杠被吞掉了。
- 对策：路径反斜杠统一换成 `/` 再传；`allowUnsafeCustomBinary: true`，放行时它会 `console.warn` 一次，创建 client 时临时静音。

### simple-git 拦截 `-c core.fsmonitor=false` 与 GIT_EDITOR

- 现象：配了 `config: ['core.fsmonitor=false']` 后报 `Configuring core.fsmonitor is not permitted without enabling allowUnsafeFsMonitor`；环境里带 `GIT_EDITOR` 时报 `Use of "GIT_EDITOR" is not permitted`。
- 原因：simple-git 的 block-unsafe-operations 插件不区分「打开」还是「关闭」fsmonitor，一律拦；`GIT_EDITOR` 等变量同样被它当成危险项。
- 对策：`allowUnsafeFsMonitor: true`（我们只会把它设成 false）；`GIT_EDITOR / EDITOR / VISUAL / GIT_ASKPASS` 等在传给子进程前从 env 里剥掉，而不是放行。

### harness 自己的 git 调用触发了恶意 fsmonitor

- 现象：verify-git 里「干净工作区 files 为空」失败，多出一个未跟踪的 `pwned.txt`；看起来像 GitService 执行了恶意 fsmonitor。
- 原因：是 harness 自己 `git stash` / `git checkout` 时执行了它配的恶意 `core.fsmonitor`，GitService 没有执行。
- 对策：harness 的 git 调用一律带 `-c core.fsmonitor=false`；断言「多次 status 后仍未执行」放在 harness 自己的 git 命令之后，才能证明是 GitService 安全。

### 回归 harness 写死了设置页签列表

- 现象：设置页加了 Git 页签后，verify-m5 的「六个页签」和 verify-layout 的页签循环会漏掉新页签。
- 对策：两处同步加上 Git；以后新增设置页签要一起改这两个脚本。

## 2026-11-06 · Git 管理 G1

### harness 直接调 settings.update 不会刷新渲染层配置
